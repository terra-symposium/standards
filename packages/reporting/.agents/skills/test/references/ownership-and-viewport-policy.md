# Test ownership and viewport selection

Assign each observable behavior to the repository that owns its implementation. Package tests prove package behavior; application tests prove application composition, authorization, persistence adapters, and integration with the package. Keep one canonical scenario for each behavior across repositories. Retain a consumer scenario only when it proves an additional boundary. Record the replacement or the reason for every retired assertion before deleting a test.

Place test files parallel to the owning source module or route. Merge sister files with the same owner and runner when they share setup and prove one journey. Use native `test.step` for related create, edit, reload, duplicate, and delete stages; keep distinct roles, failure recovery, and independent starting states as separate tests. Prefer fast unit or API assertions for pure data rules. A source-text test is appropriate only for a contract that cannot be verified more reliably through behavior, types, or build checks.

Temporary connection checks belong in a once-per-run preflight outside the regression inventory. Keep tests for active security, authorization, destructive-operation, and cleanup contracts. The suite manifest must name each executable command once and validate that discovered test files have one owner.

For each browser scenario, inspect the route's media/container queries and measure the rendered control layout. Use the canonical desktop viewport for layout-independent logic. Add a viewport only when it proves a distinct wrapping, overflow, visibility, navigation, control-placement, or interaction risk. At a layout transition, test the affected interaction immediately below, at, and above the actual threshold; add a narrow or wide extreme when it exposes another distinct risk. Do not run the full behavior journey at every width by default.

Declare selected dimensions with native Playwright `@viewport:<name>` tags and a `viewport-reason` annotation beside the test. A group-level declaration is valid only when it applies to every scenario in the group. A named viewport must exist in the suite's catalog. Use `viewportPolicy: 'declared'` in the shared Reporting helper after all tests in that suite are annotated. The helper filters projects at collection; runtime skips cannot substitute for selection. Do not mix a project-level `grep` with this policy.

Keep screenshots for meaningful UI states and identify each capture by stable scenario and step. Compare collected scenarios and selected viewport combinations with the expected inventory; historical captures remain available but must not count as current coverage. Measure browser sessions, server/build startup, fixture duration, and total wall time before and after consolidation in comparable environments. Lower test count alone does not prove a faster suite.
