---
title: Documentation authoring
description: Organise accurate, task-focused Docs pages with supported blocks.
---

Use directories for trees and numbered branches, and Markdown or MDX files for leaves. Each leaf should answer one primary reader question. Name branches in reading order, such as `0-getting-started` and `1-packages`.

For Docs document blocks and Markdown conversion, use the [Docs authoring guide](https://github.com/Terra-Symposium/docs/blob/development/src/content/docs/authoring.md).

## Choose a page type

| Reader needs           | Page type   | Include                                         |
| ---------------------- | ----------- | ----------------------------------------------- |
| A first working result | Tutorial    | Prerequisites, steps, and verification.         |
| One concrete task      | How-to      | Decision points and expected result.            |
| Exact facts            | Reference   | Exports, fields, defaults, limits, and outputs. |
| Reasons and trade-offs | Explanation | Rationale and links to procedures.              |

These are the [Diátaxis page types](https://diataxis.fr/start-here/). Split a leaf when its reader purpose changes.

## Choose a block

| Relationship                    | Block                                                            |
| ------------------------------- | ---------------------------------------------------------------- |
| Repeated properties             | Table                                                            |
| Sequence or dependency          | `<Nodes />` diagram                                              |
| Alternative instructions        | Tabs with three vertical bar delimiters and `[Title]` sections   |
| Optional detail                 | Accordion with `=== [Title]` sections                            |
| A bounded constraint or example | `:::note`, `:::tip`, `:::warning`, `:::caution`, or `:::example` |

Use a diagram only when the relationship is harder to understand in prose. Give images informative alt text and a caption. Keep assets beside their owning section.

## Verify and publish

Derive package names, exports, flags, schema fields, requirements, and side effects from manifests, declarations, implementation, or tests. Put prerequisites before commands. Keep examples runnable and avoid repeating another leaf's reference material. Use synthetic data; exclude credentials, personal data, and production payloads.

Run `pnpm run docs:build`, then inspect the built page at its real route. Check links, anchors, images, narrow layouts, and interactive blocks. Preview instructions are in [change validation](/contributing/1-quality/change-validation/).

See [recovered development notes](/contributing/2-authoring/recovered-standards/) for backup-era context; current guidance on this page remains authoritative.
