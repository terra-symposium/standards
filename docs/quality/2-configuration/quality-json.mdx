Terra Quality reads `quality.json` from the current working directory. The package includes a JSON Schema for editor completion and validation. Set `$schema` to the installed schema path; `quality.json` must use strict JSON syntax.

The configuration lifecycle is: discover the file, resolve the repository root, select source roots and extensions, then apply check and tool policy.

## Minimal configuration

This example uses built-in checks without enabling external tools:

```json
{
	"$schema": "./node_modules/@terra-symposium/standards-quality/quality.schema.json",
	"sourceRoots": ["src"],
	"extensions": [".js", ".jsx", ".ts", ".tsx"],
	"enabledChecks": {
		"format": false,
		"lint": false,
		"knip": false,
		"dead-code": false
	}
}
```

Install and configure a tool before enabling the check that invokes it. For example, linting requires an ESLint flat config at `root` or under `configRoot`. Keep builds and functional tests in separate scripts and CI steps; `qualityCommands` is for static and hygiene checks.

## Paths and source discovery

Use these two common layouts to understand the default path resolution. An explicit `root` or `configRoot` overrides the inferred location.

||| [Root-level configuration]
§§§text
repository/
├── quality.json
├── src/
└── config/
└── eslint.config.mjs
§§§

A root `quality.json` defaults the project root to its containing directory and `configRoot` to `<root>/config`.
|||

||| [Config-directory configuration]
§§§text
repository/
├── config/
│ ├── quality.json
│ └── eslint.config.mjs
└── src/
§§§

A `config/quality.json` defaults the project root to the parent directory and `configRoot` to the directory containing the configuration.
|||

The editor-only `$schema` path points to the installed JSON Schema; the runner does not read it. The table below describes the path fields.

| Field                   | Purpose                                                                                                                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `root`                  | Repository root used for source discovery and child-process working directories. Relative to the inferred project root.                                                                                 |
| `configRoot`            | Central tool-config directory searched after root-level config files for ESLint, Prettier, Knip, and the default TypeScript project. Relative to `root`; defaults based on the `quality.json` location. |
| `sourceRoots`           | Required source roots scanned by regular checks.                                                                                                                                                        |
| `includeRoots`          | Additional source roots appended to `sourceRoots` during discovery.                                                                                                                                     |
| `extensions`            | Required file extensions for source discovery, including the leading dot.                                                                                                                               |
| `aliases`               | Internal import prefixes mapped to repository paths, such as `{ "@/": "src/" }`.                                                                                                                        |
| `externalPrefixes`      | Import prefixes that the import checker should treat as external.                                                                                                                                       |
| `frameworkEntryExports` | Explicit framework-discovered exports that Knip should retain, keyed by a source file path or supported `/**/*.ts` / `/**/*.tsx` pattern.                                                               |
| `protectedIdentifiers`  | Names that naming maintenance must preserve.                                                                                                                                                            |
| `renameExports`         | Whether eligible exported names can be renamed. Defaults to `false`.                                                                                                                                    |

Quality checks scan every matching source file below the configured roots and apply only the shared package's standard dependency and generated-output exclusions, including Rust `target` output. Terra consumer configs must not add repository-specific skipped directories, skipped files, or single-use skips. If a generated or vendored file is incorrectly classified as source, fix the shared classifier or the owning generation boundary instead of carving that path out.

## Optional performance-pattern scan

Set `performancePatterns` to scan for linear collection lookups nested inside collection callbacks. This diagnostic is opt-in, advisory, and never rewrites loops or changes lookup order. Confirm the path is performance-sensitive and benchmark it before applying an indexing change.

```json
{
	"performancePatterns": {
		"extensions": [".js", ".jsx", ".ts", ".tsx"],
		"ignoredFiles": ["src/generated/client.ts"]
	}
}
```

## Check and autofix controls

Every built-in check is enabled unless its `enabledChecks` entry is `false`. Some checks need a policy block, tool, or repository command before they have work to do. Supported check names are:

```json
{
	"enabledChecks": {
		"error-boundaries": true,
		"document": true,
		"format": true,
		"import": true,
		"name": true,
		"forward": true,
		"accessibility": true,
		"display-name": true,
		"performance-patterns": true,
		"documented-commands": true,
		"lint": true,
		"knip": true,
		"dead-code": true,
		"type": true,
		"recommend": true,
		"command": true,
		"diff": true,
		"alias": true,
		"security": true,
		"repeated-classes": true,
		"regex-dedup": true,
		"ui-patterns": true,
		"github": true
	}
}
```

A missing or `true` entry enables existing checks; the new `accessibility`, `display-name`, and `documented-commands` checks require an explicit `true` during rollout. The `error-boundaries` check is mandatory and cannot be disabled. Other checks can be disabled with `false`. `--warn` disables all Terra Quality autofixes for one CLI run. To disable a particular fixer by default, set its name to `false` under `autofix`:

```json
{
	"autofix": {
		"document": true,
		"format": true,
		"name": true,
		"lint": true,
		"knip": true,
		"dead-code": true,
		"alias": true,
		"forward": true,
		"accessibility": true,
		"displayName": true,
		"documentedCommands": true,
		"repeatedClasses": true,
		"regexDedup": true
	}
}
```

The accessibility, display-name, and documented-command checks are opt-in so publishing the package does not make existing consumers fail before they have reviewed or fixed their findings. Set their `enabledChecks` entries to `true` when ready. The `error-boundaries` check is always active and its boundary fix is available in normal fix mode; use `--warn` to inspect without writes. `performance-patterns` is advisory and runs only when a `performancePatterns` settings block is present. Configure `documentation.commandRoots` to check Markdown command examples and permit the source-evident pnpm flag correction:

```json
{
	"enabledChecks": {
		"accessibility": true,
		"display-name": true,
		"documented-commands": true
	},
	"documentation": {
		"commandRoots": ["docs", "docs/agents"]
	},
	"performancePatterns": {
		"extensions": [".js", ".jsx", ".ts", ".tsx"],
		"ignoredFiles": ["src/generated/client.ts"]
	}
}
```

The performance check suggests indexing but does not make a rewrite or fail quality. Measure the representative path before deciding whether the change is worthwhile. Browser, broad integration, and benchmark checks should stay behind explicit or scheduled commands, with expensive setup shared within each suite.

The `autofix` keys use camel case for `repeatedClasses` and `regexDedup`, while `enabledChecks` uses kebab case. A missing or `true` fixer entry permits its supported fixes when the CLI is in fix mode. Individual transformations remain conservative and may leave ambiguous cases for review.

## Documentation policy

Use `documentation.required` to set declaration documentation requirements:

```json
{
	"documentation": {
		"required": {
			"types": true,
			"functions": true,
			"exportedFunctions": true,
			"noInlineFunctions": true
		}
	}
}
```

- `types` covers classes, enums, interfaces, and type aliases.
- `functions` covers named function declarations.
- `exportedFunctions` requires documentation for exported named functions and can be used when `functions` is `false`.
- `noInlineFunctions` reports arrow functions and function expressions; it has no automatic rewrite.

Documentation findings are read-only. Write missing descriptions after inspecting source and callers; Quality does not create comment scaffolds or placeholders.

## Mandatory application error boundaries

Terra Quality always checks React `createRoot()` and `hydrateRoot()` entry points for a top-level error boundary and Astro config files for the shared hydration error-boundary integration. The check is not controlled by an `enabledChecks` toggle; setting `"error-boundaries": false` is invalid. Normal fix mode can add supported wrappers and integration setup. Pass `--warn` to report missing boundaries without modifying files, or run the focused `terra-quality error-boundaries --all` command to apply the configured check directly.

The static check cannot prove that the fallback is appropriate, that every nested render root has meaningful recovery, or that runtime failures are handled. Exercise the React and Astro paths in browser tests. See [React boundary behavior](/error-boundaries/1-react/react-boundaries/) and [Astro hydration handling](/error-boundaries/2-frameworks/hydration/).

## Tools and TypeScript

| Field                 | Purpose                                                                                                                      |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `tools.prettier`      | Prettier executable used for formatting.                                                                                     |
| `tools.eslint`        | ESLint executable used by lint and coordinated dead-code analysis.                                                           |
| `tools.knip`          | Knip executable used for reachability and dead-code analysis.                                                                |
| `tools.tsc`           | TypeScript executable used for type checks.                                                                                  |
| `oneLineImports`      | Enables the source-maintenance protection for configured long one-line imports.                                              |
| `prettierPrintWidth`  | Print width used by the one-line import protection.                                                                          |
| `lintRoots`           | Additional ESLint roots; when omitted, the selected source files define the lint scope.                                      |
| `tsconfig`            | TypeScript project configuration path relative to `root`; defaults to root `tsconfig.json`, then `configRoot/tsconfig.json`. |
| `typecheckRoots`      | Restricts selected-file type checking to these roots.                                                                        |
| `typecheckExtensions` | Extensions included in selected-file type checks.                                                                            |
| `typecheckCommand`    | Repository-owned typecheck executable and optional string-array arguments.                                                   |

Tool names are resolved from `<root>/node_modules/.bin` first, then from the environment's command path. A configured path containing a slash is used as given. Terra Quality does not install tools or define their native rules. A full project type check runs when `tools.tsc` is configured; the focused `types` command uses `tsc` by default.

## Repository commands

`qualityCommands` contains repository-owned static or hygiene checks that are not covered by a built-in check. Never put a build, unit test, integration test, contract test, browser test, Playwright test, or example execution here, directly or through a wrapper. Keep `build` and `test` as separate scripts and CI workflow steps so their results are independently actionable. Each command entry requires a unique lowercase `name` and a `command`; `args` is an optional array of strings. Terra Quality assigns static commands to its fixed full-run phases and preserves configured order within each phase; configuration does not define ordering or category fields.

```json
{
	"qualityCommands": [{ "name": "c-doc-params", "command": "make", "args": ["check-doc-params"] }],
	"enabledCommands": { "c-doc-params": true }
}
```

Use `enabledCommands` to toggle one configured static command. Set `enabledChecks.command` to `false` to disable the category or pass `--skip-commands` for one run.

`recommendationCommands` uses the same entry shape. Use `enabledRecommendations` to toggle a command or `enabledChecks.recommend` to disable all recommendation commands. A nonzero subprocess status fails the quality run. Pass `--skip-recommendations` to omit these commands once.

Commands run from `root`, inherit the caller's environment, and are not automatically limited to changed files. The runner does not provision credentials, databases, browsers, or other services.

## GitHub analytics

| Field    | Options                            | Purpose                                                                |
| -------- | ---------------------------------- | ---------------------------------------------------------------------- |
| `github` | `repositories`, `requiredFeatures` | Include read-only GitHub analytics in the quality run and JSON report. |

`github.repositories` is an array of `owner/name` slugs. The report reads open issues and pull requests, Dependabot vulnerability and malware alerts, code scanning and secret scanning alerts, repository settings available to the authenticated identity, and version-update configuration from the default branch's `dependabot.yml`. An explicit `groups` rule with `applies-to: security-updates` verifies grouped security updates; without one, the report marks the UI-level grouping setting unverified for confirmation in repository settings. `requiredFeatures` can name `dependencyGraph`, `dependabotAlerts`, `malwareAlerts`, `securityUpdates`, `versionUpdates`, `groupedUpdates`, `secretScanning`, `pushProtection`, or `codeScanning`. Required settings that are disabled or unverifiable become findings. An unavailable or disabled endpoint has a `null` count, not a zero. Authenticate the local GitHub CLI with read access; this check does not need Actions or write permissions.

## Security and source-pattern policies

These checks require the corresponding policy object. See [check behavior](/quality/0-getting-started/overview/#repository-policies-and-patterns) before enabling them.

| Field               | Options                                                             | Purpose                                                                                                                                                                   |
| ------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `security`          | `forbiddenTerms`, `forbiddenImports`, `clientRoots`, `runtimeRoots` | Report configured terms/imports, root-level or committed environment files, secret-shaped access in client roots, and process-environment use outside Node runtime roots. |
| `repeatedClasses`   | `minimumCount`, `extensions`                                        | Find repeated static class strings in selected source files.                                                                                                              |
| `regexDedup`        | `minimumCount`, `extensions`, `sharedModule`                        | Find duplicate regex sources; an optional repository-relative `.mjs` module with a matching `.d.mts` declaration supports shared extraction.                              |
| `uiPatterns`        | `forbidden`, `extensions`                                           | Report configured UI source patterns for review.                                                                                                                          |
| `uiRecommendations` | `rules`, `extensions`, `ignoredFiles`, `ignoredDirectories`         | Configure the on-demand Astro/JSX shared-component recommendation report.                                                                                                 |
| `tailwindCanonical` | required `stylesheet`, optional `sourceRoots`                       | Configure the Tailwind v4 canonical-class check and autofix.                                                                                                              |

Configured repositories run `tailwind-canonical` during the normal quality command. Set `enabledChecks["tailwind-canonical"]` to `false` to disable it, or `autofix.tailwindCanonical` to `false` to retain diagnostics without writes. The standalone command is `terra-quality tailwind-canonical`; add `--warn` for a read-only check. The API remains exported as `runTailwindCanonical(cfg, fix?)`. See [Tailwind canonical classes](/quality/0-getting-started/overview/#tailwind-canonical-classes) for examples and Tailwind v4 compatibility details.

Example:

```json
{
	"security": {
		"forbiddenTerms": ["temporary-secret"],
		"forbiddenImports": ["unsafe-package"],
		"clientRoots": ["src/client"],
		"runtimeRoots": ["src/server", "scripts", "tests"]
	},
	"repeatedClasses": { "minimumCount": 3 },
	"regexDedup": { "minimumCount": 2 },
	"uiPatterns": { "forbidden": ["className=\\\"legacy-button\\\""] }
}
```

These portable checks are policy guardrails, not a complete secret scanner, framework-aware analysis, or proof that an application is secure.

`security.runtimeRoots` declares positive Node-only files and directories that own `process.env` reads, including server code, tooling, and test harnesses. The former `security.allowProcessEnvRoots` field remains accepted as a compatibility alias; migrate it to `runtimeRoots` when updating existing configurations.

## Load timing

`loadTesting` is read by `@terra-symposium/standards-reporting`. Load timing is enabled by default with a warning threshold of 2,000 ms and a failure threshold of 5,000 ms.

```json
{
	"loadTesting": {
		"enabled": true,
		"defaultBudget": { "warnMs": 2000, "failMs": 5000 },
		"testBudgets": {
			"tests/dashboard.spec.ts::Dashboard loads": { "warnMs": 5000, "failMs": 10000 }
		},
		"operationBudgets": {
			"bulk import": { "warnMs": 5000, "failMs": 12000 }
		}
	}
}
```

Budget values are milliseconds; `failMs` must be greater than `warnMs`. Test budget keys use `<repo-relative file>::<full title path>`; operation keys match the measurement name. Test-local overrides take precedence over configured test budgets, which take precedence over the default. Disable `loadTesting.enabled` to stop collecting and enforcing new measurements while retaining the visual reports.

## This repository's configuration

The root [`quality.json`](https://github.com/Terra-Symposium/standards/blob/main/quality.json) scans `packages` and `scripts`, enables several project-specific checks, preserves long one-line imports, and declares build and test commands. It excludes single-use analysis from `packages/quality`, where reusable declarations and package APIs are intentionally concentrated. Use it as a reference, then choose scope and rules that fit your repository. Repositories may instead keep the quality file and related tool configs together under `config/`; Terra Quality infers the repository root and discovers the tool configs there.
