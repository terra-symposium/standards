# npm package publishing

Terra package releases run through the Standards GitHub Actions workflow. Maintainers can publish without an npm login on their computer. The workflow reads its publisher credential from the Standards repository secret named PACKAGES_TOKEN. Keep that value private; never print it or put it in source, logs, or artifacts.

## The central publisher

The workflow at .github/workflows/publish-packages.yml is the single Terra publisher. It builds and publishes the four Standards packages plus @terra-symposium/docs. All five publishing steps use PACKAGES_TOKEN. Do not create separate npm tokens or trusted-publisher connections for individual repositories.

The workflow gets Docs source from Terra-Symposium/docs at an explicit 40-character commit SHA. It validates the SHA format, checks out that exact revision, installs from the repository's config lockfile, builds the package, and verifies the package name before publishing. The Standards packages are built from the checked out Standards revision.

The secret exists in the Standards repository, but its name alone does not prove npm grants write access to every package. The token must have publish access to all five package names. If a publish returns 403 or 404, keep the workflow and credential centralized; resolve the npm token's scope for that package rather than adding another publisher. Do not paste or expose the token to diagnose it.

## Release a package

1. Update the package version and release notes in its source repository, then merge the reviewed change.
2. For Docs, identify the full 40-character commit SHA to publish. Open the Standards repository's Actions tab and run **Publish shared packages** with that SHA. The default SHA is a known Docs revision; replace it with the reviewed release revision when needed.
3. Confirm each expected package and version in the workflow output. The workflow skips a version that npm already has.
4. Verify the published version on npm, then update consumers and lockfiles.

The workflow does not accept a repository URL or arbitrary package name. This keeps the publisher limited to the configured Terra packages. Never overwrite or unpublish an existing release; publish a new version instead.

## Trusted publishers and OIDC

npm trusted publishing uses GitHub OIDC instead of a token, but each trusted-publisher configuration is package-specific. It cannot serve as one publisher for every Terra package. Terra uses the central Standards workflow and its one repository secret for this reason.

An OIDC exchange 404 such as package not found indicates npm did not match the package and publisher configuration. Do not create another per-package connection as a workaround; use the shared publisher described above.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| ENEEDAUTH | Confirm the central workflow references PACKAGES_TOKEN and that the Actions secret remains configured. |
| Publish returns 403/404 | The token may lack write access to that package. Resolve access for the central token; do not create a second publisher. |
| Version already exists | Verify that version on npm. Release a new version if further changes are needed. |
| Docs checkout fails | Supply a valid full 40-character commit SHA from Terra-Symposium/docs. |
| Docs build fails | Check the selected revision and the repository's config lockfile and build workflow. |

Keep the credential only in Standards Actions secrets. Do not copy it to consumer repositories, workflow text, .npmrc, logs, or build artifacts. Rotate the central credential through npm's account process and update PACKAGES_TOKEN without exposing its value.
