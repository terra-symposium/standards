# npm package publishing

Terra publishes npm packages through GitHub Actions. Maintainers trigger releases in GitHub; the workflow reads its configured credential from Actions secrets. A local npm login or repeated browser sign-in is not part of the release process. Never print, copy, or commit the secret value.

## The shared publisher

The Standards repository owns the current shared publisher workflow at `.github/workflows/publish-packages.yml`. It reads `secrets.NPM_TOKEN` and currently publishes four packages from this repository: `@terra-symposium/standards-quality`, `@terra-symposium/standards-error-boundaries`, `@terra-symposium/standards-reporting`, and `@terra-symposium/standards-testing`. The root `.npmrc` only selects npmjs.org for the `@terra-symposium` scope and sets public access; it does not grant publish permission.

Keep one controlled publishing credential in the Standards repository and route Terra releases through the shared workflow. Add each package to the workflow's explicit allowlist, checkout its public source at a pinned ref, build it, and publish only when that exact version is not already present. Do not create a separate npm token or publisher workflow in every consumer repository. Keep the credential as a GitHub Actions secret and grant it only the Terra package scope needed for publishing.

The current workflow does not yet publish packages outside the Standards checkout. Adding Docs requires an explicit allowlisted Docs source and package entry, and the existing `NPM_TOKEN` must already be authorized for `@terra-symposium/docs`. The secret value is intentionally not inspected. If npm rejects a publish with 404 or 403, check token package access and package ownership in npm, then update that single credential's package scope through the approved account process.

## npm trusted publishers

An npm trusted publisher uses GitHub OIDC and does not need an npm token, but npm associates the trust connection with an individual package. A connection configured for one package cannot publish every Terra package. Each package would need its own npm trusted-publisher connection, so this is not Terra's shared-publisher model. An OIDC token-exchange 404 such as `package not found` means npm did not match the request to an authorized package/publisher connection; verify the package, organization, repository, workflow filename, and configured environment. Do not keep retrying the same unmatched connection.

## Release procedure

1. Update the package version and release notes in its owning repository.
2. Merge the reviewed change to the release branch.
3. Run the Standards `Publish shared packages` workflow, selecting only an allowlisted package and immutable source ref.
4. Confirm the workflow reports the expected package name and version, then verify that version on npmjs.org.
5. Update consumer dependency ranges and lockfiles only after the version is visible on npm.

The workflow must fail closed for unknown package names, use immutable refs, build from a clean checkout, and avoid logging credentials. `npm view` may be used to skip a version that is already published; never overwrite or unpublish a released version to recover a failed run.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `ENEEDAUTH` | Ensure the workflow uses the Standards secret and npm CLI supports the selected authentication method. |
| OIDC exchange returns 404 | Confirm the package-specific trusted-publisher fields, or route the release through the shared token workflow. |
| Publish returns 403/404 | Confirm `NPM_TOKEN` has write access to that package and the package belongs to the Terra scope. |
| Version already exists | Verify it on npm and move to the next patch version; npm versions are immutable. |
| `npm view` fails in CI | Check registry connectivity and distinguish an absent version from authentication/network errors before publishing. |

## Security

Keep `NPM_TOKEN` only in GitHub Actions secrets for the central publisher. Do not add it to consumer repositories, workflow text, logs, artifacts, or `.npmrc`. Use a granular automation token scoped to Terra packages, with publish access only; rotate it through the npm account process and update the single central secret. Prefer npm trusted publishing only when configuring and maintaining one trust connection per package is acceptable.
